 - LVGL display: power saving mode - the backlight is dimmed to a second brightness level after an idle timeout and the display is turned off after the standby timeout. Every brightness change is faded to the new level (the full 0-100% range takes 3 seconds) and the touch that wakes the display up is not passed to the UI. A motion/presence sensor can wake it up through `LVGLPlugin::notifyActivity()`
 - Web server: a response that used `AsyncBaseResponse` (`/lvgl-screen.bmp`, `/file_manager/list`, the directory listing, the core dump, ...) was **cut short when the send buffer was full**: `_ack()` asked the source for 0 bytes (there was no room for more) and took the empty result as the end of the content, so the response finished although most of it was never sent. The client kept waiting for the rest of its `Content-Length`, timed out and aborted the connection - the debug screenshot of 460 KB stopped after a few KB, took minutes or never finished, and the connection it left behind kept the device busy (a client that aborts in the middle of a response is what made the network stack run out of buffers, see the notes on the debug screenshot feature). The state now stays `RESPONSE_CONTENT` until the whole content was handed to the client and only the last chunk ends the response (a 460 KB screenshot takes 1.5 seconds instead of stalling). The debug screenshot response also tears its connection down at once when the client stops acknowledging the data (`setAckTimeout`, the timeout handler aborts it) - a client that gave up no longer leaves a connection behind that keeps the lwIP buffers busy for about a minute
 - Home Assistant dashboard: fixed the pushed values that never arrived for a page whose tiles are all `switch`, `light` or `button` tiles (the tiles stayed on `...` while the same entities drove the other pages correctly). A `render_template` render is answered as a **string** only while that text is not valid JSON: the template of a page is a JSON object and every value it writes is one, so Home Assistant parses the render and sends the **object** back (`"result":{"light.strip.state":"off"}` instead of `"result":"{\"light.strip.state\":\"off\"}"`). The socket only read the string form and dropped the object one silently (an empty result ends `_takePushedTemplate()`), and a page whose entries are all states renders valid JSON - which is why only those tiles were affected. Both forms are handed to the dashboard as the text of the JSON it walks now (`Socket::_resultText()`, the nesting is followed so a comma inside a value does not end it), so a value is read the same way no matter which form it arrived in. The event object of Home Assistant collapses the entries that repeat (six tiles of the same entity arrive as one member), which is what the tiles of a shared entity rely on
 - Home Assistant dashboard: an entity that several tiles use is **applied to all of them**, also to the tiles of a page that is not shown right now (page 23 shows 21 tiles of `light.led_strip_xmas_led_strip` in this configuration and every one of them follows the push). Before, only the tiles of the visible page were updated, so a page showed the state from before a change until its own subscription answered. A response carries the page it was built from (`Dashboard::_applyResponse(payload, page)`): a tile of that page whose entity is missing from the answer is `unavailable` (as before), a tile of **another** page keeps what it has - the response simply does not carry its entity. That also fixes the tiles of a page that was just opened being marked `--`/`...` by the answer of the page that was left: the client stamps every subscription with the page its template was built from (`Socket::subscribeTemplate(template, page)`, `takeTemplateResult(text, error, page)`) and the dashboard leaves the tiles of every other page alone
 - Home Assistant dashboard: the fill and the glyph of a tile are redrawn when the entity state, the pending mark **or** the active state changes (`_arcState` holds all three now). Only the state was the key, so a tile whose entity reported `off` while an action was on its way kept the fill and the glyph of `on` - the text said "Off", the tile stayed lit and the border showed the pending color, exactly what a quick tap on and off looks like. The pending mark of a tile that left the screen also ends now (the timeout of `_markPending()`), so a mark that is never confirmed by a response cannot pulse in that color forever
 - Home Assistant dashboard: a subscription that Home Assistant **rejected** is reported instead of leaving the client waiting for events that never come (`"result","success":false,"error":{...}` for the id of the subscription is read as an error of the template, the subscription is given up and the client subscribes again), and a connection that stops answering is torn down after 70 seconds - the API answers every ping, so a longer silence means the socket is not usable any more even though it still looks open (the values it should push never arrive, nothing reports an error). The trace logs every message that arrives with its id and length (`hass> ws< event id=7 (187 bytes, template 7)`), which is what told the two apart
 - Home Assistant dashboard: the client no longer subscribes the template of the page that was **left** while the page that is opened is being built (`Client::_templatePage == _visiblePage`). A page change marked the template dirty and set the flag to subscribe again, and the subscribe of that iteration could still use the template of the old page (its answer was then applied to the tiles of the new page)
 - Home Assistant dashboard: the values of the tiles are **pushed** instead of polled - one websocket connection of the screen subscribes the template of the visible page (`render_template`) and Home Assistant sends the rendered result when one of the entities it reads changes, and only when the result differs from the previous one. The connection replaces the `POST /api/template` per refresh (a new TCP connection, and with `https` a TLS handshake per poll), the actions are `call_service` on the same connection and the attributes of an open panel are part of the subscribed template (the second request of a panel is gone). The periodic `hass.poll` (default is a minute now) subscribes the template again as the safety net of the subscription, a connection is opened again with a backoff of 2..30 seconds and a panel that lost its connection recovers by itself. The history graph of the sensor panel uses the same connection
 - Home Assistant dashboard: a `sensor` tile opens a **sensor panel** with the live state of the entity and its **history graph** over the last 12, 24 (default) or 48 hours (three range buttons, refreshed every 5 minutes while the panel is open). The history comes from the long term statistics of the recorder over the **websocket API** (`recorder/statistics_during_period`, 5 minute buckets, `mean` only, nothing stored on the device): the window is requested in six hour chunks because the receive path of the ESP32 stops handing over a single message larger than about 8 KB (a 48 hour answer is 32 KB) - the chunks are requests of their own on one connection, a chunk that is not answered in time is retried on a new one and a window that cannot be read completely is drawn from the buckets that arrived. One column per bucket, the Y axis follows the data (three labels), six time labels on the X axis, an entity without long term statistics shows "No history for this entity"
 - Home Assistant dashboard: the orientation of the dashboard is selectable on its own page of the WebUI (`/weather2-hass.html`, "Home Assistant") - landscape (480x320, the default), portrait (320x480) and both turned 180 degrees. Only the dashboard is rotated: the display is switched in `HassScreen::create()` and switched back to landscape in `release()`, so the other screens, their panels and the screen list stay landscape. The grid of `/hass.yaml` is written for the landscape layout and is transposed in portrait (`cols`/`rows` and the position and span of every tile are swapped, 4x3 becomes 3x4), so the file does not have to change with the orientation, and the panels clamp their fixed controls (climate arc, level slider, color wheel, the value column of the sensor panel) to the narrower column. The setting is its own configuration parameter (`WeatherStation::getHassRotation()`, no reboot and no reset of the weather configuration) and `WT32_SC01::setRotation()` switches the panel and the LVGL resolution at runtime (`lv_disp_drv_update()`, the draw buffers cover both orientations without a reallocation)
 - Weather Station v2: the configuration form is split into four pages (`/weather2.html`, `/weather2-sensors.html`, `/weather2-power.html`, `/weather2-hass.html`) with one menu entry each. The complete form is created before the response is streamed, so a page with ~40 fields is rendered in one go and one page that fails blocks the whole request - every group is a form of its own now and the pages can be opened independently
 - Fixed the page responses that stopped in the middle and left the device unreachable: a frame was built for the whole free space of the connection and handed to the socket in one write, while the send buffer of the network stack can shrink *while* the content is produced (rendering a form page takes seconds and the stack is short of buffers when MQTT, the websocket and the logger run) - everything above the send buffer was silently dropped, the response counted it as sent and the client waited forever for data that was never queued, which kept the abandoned connection and its buffers busy until the network stack had nothing left (`[E][WiFiUdp.cpp:185] endPacket(): could not send data: 12` = ENOMEM, MQTT disconnected, no page could be opened). `AsyncBaseResponse` now sends one frame of at most 1 KB per call (one TCP segment, `kMaxFrameSize`) and keeps the rest for the next call instead of dropping it
 - Weather Station v2: the Home Assistant dashboard and the screen that draws it (about 47 KB and 8 KB - the parsed `/hass.yaml`, the value and history of every tile, the request buffers and the widget tree) are created in the **PSRAM** instead of the internal DRAM (`_ws2PsramObject()`, which also initializes the PSRAM: the plugin instance is a static object and its constructor runs before `initArduino()`). The static RAM of the firmware drops from 118,004 bytes (36.0 %) to 63,204 bytes (19.3 %) and the free internal DRAM grows by about 55 KB (~100 KB -> ~154 KB at boot), which is what the network stack, the LVGL buffers and the task stacks all compete for
 - Home Assistant dashboard: fixed the layout that was clipped after a live orientation change - `HassScreen::_applyOrientation()` updated the metrics and rotated the display, but the grid container and the two labels above it (created by `create()` and reused by every `_rebuild()`) kept the size of the orientation they were built with, so the new layout was laid out correctly and then cut off by the smaller container (the 480 px wide landscape design was clipped at a 320 px wide container and the bottom rows of the portrait layout were cut at 320 px tall). A screen reload hid it, which is why it looked intermittent. The containers are resized with the new orientation now
 - Home Assistant dashboard: the light and climate panels are laid out for **portrait** on their own. A landscape panel puts the back tile and the options into the left column of the grid (the width of one cell) and the header and the control into the right one, but the portrait grid transposes the cells into four rows, so that column covered only half of the display and the control was squeezed into the left half of it (the level slider in a 64 px column, the climate arc 68 px). The portrait panel is stacked in rows over the whole width with a gap of 12 px between them (`HassScreen::_panelLayout()`): header row (back tile and name), then for a **climate** the arc over the whole width, the row `-` `+` and the options at the bottom, and for a **light** the big readout, the slider with its two steppers and the options. Every gap the eye sees is 12..20 px, nothing is centered in a band of leftover space. The landscape layout is unchanged (verified pixel-identical)
 - Home Assistant dashboard: a **thicker ring** (the band) for the climate arc (`kPanelArcRing` 27 px - the `kArcWidth` 18 px of a tile, + a quarter twice; `LVGLUI::createArc()` takes the width of the ring as an argument now and the knob follows it, the arcs of the tiles keep 18 px). The diameter is not touched: the landscape arc stays 254 px (the maximum of its 258 px control area, steppers stacked at its right) and the portrait one keeps the whole width of the display. Only the portrait arc grew with the redesign: it was 224 px in the cramped cell column and is 304 px now
 - Home Assistant dashboard: the light panel in **portrait** puts the level right above the slider - the percentage (the colour temperature in the other view) is a row of its own under the header (`HassScreen::_panelValueFont()`: `kFontHuge` 32 px in portrait, `kFontValue` 28 px in landscape, the row is as tall as its text so the gaps around it are the plain 12 px) and the **slider fills the band** between that row and the options, with the round steppers centered on it at its ends (minus left, plus right, the order of the bars of a tile). The slider is 12 % narrower than the space between the two steppers (133x308 px) and stays centered between them, so the gap on either side of it grows evenly from 12 px to about 21 px; its track keeps rounded corners (34 px) while the fill that follows the level is nearly square (5 px) - a rounded fill looked like a blob inside the rounded track (`kPanelSliderNarrow`/`kPanelSliderRadius`/`kPanelSliderFillRadius`, `createPanelSlider()` takes the radius of the track and the one of the fill as arguments now). The colour wheel uses the same band
 - Home Assistant dashboard: the time labels below the history graph of the sensor panel overlapped each other and the right one ran over the edge of the card in portrait - six labels with a fixed 60 px box are 50 px apart on the 250 px wide graph of a portrait display. The number of labels follows the orientation now (six in landscape, every second divider in portrait, `HassScreen::_timeLabelCount()`) and the box of a label is as wide as the step between two of them, so no label crosses the border of the card in either orientation
 - Web server: `AsyncBaseResponse` builds its output in **one reusable window** now (`PrintBuffer _out` with a `_outSent` cursor, plus `Buffer::advance()`) instead of a `String _head`, a `Buffer _pending` and a `new uint8_t[]` for every frame. The head is printed straight into the window (no temporary `PrintString`), the content is written behind a fixed width chunk header (`"%05x\r\n"` - leading zeros are valid for the chunk size and for the last chunk) and the header is put in front of it, so nothing has to be moved afterwards and one response allocates once (1 KB) instead of ~900 times for a 460 KB transfer. A frame is only built after the previous one was handed to the socket and the rest stays in the window for the next call (`RESPONSE_TRY_AGAIN` commits nothing), the terminating `0` chunk of a chunked response is emitted exactly once, and the header path no longer drops bytes when the socket accepts less than `space()`. Every write passes `ASYNC_WRITE_FLAG_COPY` (the ESP32 default; on the ESP8266 the stack keeps a pointer into the window, which is reused for the next frame). `AsyncDirResponse` generates one JSON fragment at a time (the `goto` driven flow and `_sendBufferPartially()` are gone) and `SSIProxyStream` refills from a member scratch buffer (512 bytes, was one `new uint32_t[128]` and `free` per refill - about 900 pairs for a 460 KB page) and shrinks its buffer only every 32 refills with more than 1 KB of unused space instead of reallocating on every refill. Verified A/B on the same ESP32 (old implementation built from the previous commit): the 460 KB screenshot of `/lvgl-screen.bmp` and a 512 KB download transfer at the same ~16 KB/s, template pages (chunked + SSI), the directory listing, the WiFi scan, zeroconf, the core dump download and the same responses on the ESP8266 (`bme280_serial`) all complete with the correct length and without a single allocation per frame. The connection is closed when the response ended (`RESPONSE_END`, after the last bytes were acknowledged - closing with unsent data would reset the connection) for every response, not only for an unknown-length non-chunked one, so a client that waits for the end of the connection no longer sits in its own timeout - that trailing wait made every raw socket measurement look about twice as slow, the response itself was always complete
 - Web server: `AsyncBaseResponse` fills the send buffer of the connection in every call now instead of handing over a single frame (up to `kMaxProduceTime` = 25 ms per call, the rest is produced by the next acknowledgement or poll). Producing one frame per call left the ~5.7 KB windows (`tcp_sndbuf`) of the connection almost empty and waited for an acknowledgement after every 1 KB, which capped the transfer rate at about 15 KB/s - the 460 KB screenshot of the LVGL debug page and the speed test now transfer at 250-400 KB/s again (measured on the ESP32: 356-436 KB/s for 256/512 KB, 283 KB/s for the 460 KB BMP, the ESP8266 is unchanged at 116-128 KB/s)
 - Fixed a response that was **cut short** when a refill of `SSIProxyStream` ended with a template token: the buffer behind the token is removed (its output is not available yet) and `read()` returned 0 for the empty buffer although the stream had more content - the response ended there, so pages with a token at a chunk boundary (the device name in `/status.html` was the first one) lost everything behind it. `read()`/`peek()` retry while the file or a template can still deliver data now
