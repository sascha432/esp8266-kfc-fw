# KFC-SA-2026-0001: ESP8266mDNS (LEAmDNS) remote reboot via oversized RDLength

| | |
|---|---|
| **CVE ID** | not assigned (internal ID KFC-SA-2026-0001) |
| **Component** | ESP8266 Arduino core, `libraries/ESP8266mDNS` (LEAmDNS), `src/LEAmDNS_Transfer.cpp` |
| **Affected** | ESP8266 Arduino core 3.1.2 (PlatformIO `framework-arduinoespressif8266` 3.30102.0); the same code is still in upstream `master` (checked 2026-10-18) |
| **Weakness** | CWE-789 (memory allocation with excessive size value), CWE-125 (out-of-bounds read) |
| **CVSS 3.1** | 6.5 Medium, `AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H` |
| **Impact** | Denial of service: one multicast packet reboots every ESP8266 that runs the mDNS responder on the network segment |
| **Fixed in** | kfc_fw `lib/ESP8266mDNS` 1.2.0-kfc2 (patch below; the first fix 1.2.0-kfc1 was incomplete, see "Bypass of the first fix") |
| **Discovered** | 2026-10-18, observed in the field (dozens of devices rebooted at the same time) |

## Summary

The mDNS responder of the ESP8266 Arduino core reads the 16-bit RDLength of a resource record from the packet and allocates
that many bytes without checking it against the size of the packet. A record of an unknown type with an RDLength of, for
example, 0xE000 makes `_readRRAnswerGeneric()` call `new unsigned char[57344]`. That allocation can never succeed on an
ESP8266, and the core aborts on a failed `new`, so the device reboots.

The records are parsed for **every query** the responder receives (the known-answer section is read in
`MDNSResponder::_parseQuery()` before anything is matched), so no service has to match and no query has to be running. A
single packet to 224.0.0.251:5353 reaches every device on the link at once. No authentication is involved.

## Details

### 1. Unchecked RDLength (crash)

`MDNSResponder::_readRRAnswer()` reads type, class, TTL and RDLength and passes RDLength on to the record readers:

```cpp
if ((_readRRHeader(header)) && (_udpRead32(u32TTL)) && (_udpRead16(u16RDLength)))
```

Two readers allocate RDLength bytes before they read anything:

- `_readRRAnswerGeneric()` (every record type other than A, PTR, TXT, SRV): `new unsigned char[p_u16RDLength]`
- `_readRRAnswerTXT()`: `new unsigned char[p_u16RDLength]`

The only later check is that `_udpReadBuffer()` fails if the packet holds fewer bytes; the size check that was meant
for it is commented out (`true /*m_pUDPContext->getSize() > p_stLength*/`). The allocation happens first, so the check
never gets a chance to run.

### 2. TXT items read past their buffer

`_readRRAnswerTXT()` copies the RDATA into a heap buffer of exactly RDLength bytes (not NUL terminated) and then walks
its items:

- The length byte of an item is not checked against the rest of the buffer.
- The `=` of a `key=value` item is searched with `os_strchr()`, which scans until it finds a NUL byte, past the item
  and past the end of the heap buffer.
- If the `=` is found behind the item, `ucValueLength = ucLength - (pucEqualSign - pucCursor + 1)` wraps around in
  8-bit arithmetic, and `setValue()` copies up to 255 bytes from behind the item.

This is an out-of-bounds heap read. It can crash the device, and heap bytes can end up in a stored TXT value.

## Trigger

An mDNS message (QR = 0, query) with `ANCOUNT >= 1` whose answer record:

- uses a type the responder has no reader for (handled by the generic reader), and
- has an RDLength larger than the free heap (for example 0xE000), regardless of the actual packet length.

The crash observed in the field came from a malformed packet that was multicast by accident (a reused lwIP pbuf
that most likely still carried old IP/UDP headers in front of the DNS message). The responders parsed it as a record
with RDLength 0xE000 (57344 bytes, taken from the crash logs). The SaveCrash logs of the rebooted devices match the times the packets were sent.

## Proof of concept

`KFC-SA-2026-0001.py` (next to this file) sends one unicast packet with the crafted record to a single device, so a
test does not reboot the whole network segment. It is written for Windows (`ping -n 1 -w 1000`) and only prints the
liveness samples:

```python

#
```

Usage: `python KFC-SA-2026-0001.py <ip>`. The device reboots within the sampling window and is reachable again after
it, which the last line confirms.

The packet is a query (`QR = 0`, `ANCOUNT = 1`) that asks for `_services._dns-sd._udp.local` PTR and appends one
answer of the unregistered type 99 with RDLength 0xE000 (57344) and only 4 bytes of RDATA. On a vulnerable build the
generic reader allocates 57344 bytes, the allocation fails, and the core aborts with

```
User exception (panic/abort/assert)
last failed alloc call: 40282285(57344)
```

`40282285` is the call site of the `new unsigned char[p_u16RDLength]` in `_readRRAnswerGeneric()` and
`57344` (= 0xE000) is the attacker-chosen RDLength - the same signature that appeared in the SaveCrash logs of the
devices that rebooted in the field. A patched build (`1.2.0-kfc2`) drops the message in `_readRRAnswer()` at the
`MDNS_RRANSWER_RDLENGTH_MAX` check and stays up for all samples.

## Bypass of the first fix (1.2.0-kfc1)

The first fix only compared RDLength against the bytes left in the packet
(`u16RDLength <= m_pUDPContext->getSize()`). `UdpContext::getSize()` returns `_rx_buf_size - _rx_buf_offset`,
and `_rx_buf_size` is `pbuf::tot_len` - the length of the **whole** received datagram, which lwIP builds up to
~64 KB from IP fragments. So the check is bypassed by padding the packet to the length it claims: a fragmented
UDP datagram that really carries 0xE000 bytes of trailing data passes `u16RDLength <= getSize()`, and
`_readRRAnswerGeneric()` / `_readRRAnswerTXT()` still call `new unsigned char[57344]`. The allocation aborts on
OOM exactly as before. The `if (pucBuffer)` / `&& (... = new ...)` null-checks in those readers are dead code on
the ESP8266: the core's `operator new` aborts on failure rather than returning `nullptr`, which is why the device
reboots instead of dropping the record.

The devices kept rebooting under this padded variant after 1.2.0-kfc1 was deployed.

## Fix

Three checks, all in `src/LEAmDNS_Transfer.cpp`:

1. `_readRRAnswer()` rejects a record whose RDLength is larger than the bytes left in the packet **and** larger
   than `MDNS_RRANSWER_RDLENGTH_MAX` (= `MDNS_SERVICE_TXT_MAXLENGTH`, 1300 - the largest RDATA this responder ever
   parses, a TXT record). The hard cap is the one that actually prevents the oversized allocation; the packet-size
   check stays as a cheap early reject. Known answers are created and deleted one at a time
   (`_parseQuery()` does `delete pKnownRRAnswer` every iteration), so the cap bounds the peak allocation to one
   transient ~1.3 KB buffer. This one check covers both allocating readers (generic and TXT).
2. `_readRRAnswerTXT()` rejects an item that does not fit into the RDATA, and searches the `=` with `memchr()`
   limited to the item.

A record that fails a check makes the message invalid; the existing error paths free everything that was read and
drop the rest of the packet. Capping at the max TXT length drops only answers larger than anything this responder
can use (unknown record types are read solely to skip them), so legitimate mDNS traffic is unaffected.

`UdpContext::getSize()` returns the bytes left in the current receive buffer (`_rx_buf_size - _rx_buf_offset`), where
`_rx_buf_size` is `pbuf::tot_len`, the length of the whole received datagram (up to ~64 KB after IP reassembly) - not
of a single MTU, which is why an attacker can pad the packet to match an oversized RDLength and the packet-size check
alone does not stop the allocation.

## Workaround without patching the core

Applications that cannot replace the core library can drop malformed mDNS packets before the responder sees them: wrap
lwIP's `udp_input()` (`-Wl,--wrap=udp_input`) and check that every name, question and record of a packet to port 5353
lies inside the packet. kfc_fw used such a filter as a stopgap and removed it once the patched library was in place
(do not use both).

Devices that run firmware built before the fix stay vulnerable until they are updated.
